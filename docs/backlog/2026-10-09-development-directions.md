# Направления развития Pact

Дата: 2026-10-09. Статус: черновик для обсуждения; это не спецификация и не план реализации.

## Цель и границы

Pact помогает человеку вести несколько **видимых кодовых TUI-сессий** и вовремя
возвращаться к ним. Новые возможности должны сокращать ручную работу и ошибки
при отправке запроса, отслеживании состояния и проверке результата. Сессии
продолжают работать в bundled ConPTY; сценарии, оркестратор и удалённый клиент
обращаются к уже запущенным сессиям через их терминал.

Приоритеты ниже отражают зависимость и частоту описанных проблем, а не оценку
трудозатрат. Каждая инициатива требует отдельного проектирования перед кодом.

## Перед работой по бэклогу: архитектурный анализ

Прежде чем браться за пункты ниже, провести архитектурный анализ кода:
найти места, где смешаны ответственности, дублируется логика и решения
принимаются не там, где лежат данные. Результат — карта проблем и целевое
разделение ответственностей, на которое будут опираться рефакторинг
доставки, сценариев и остальные пункты.

Пример, найденный 2026-10-12, — `SessionRuntimeCoordinator` (≈1100 строк):

- в одном классе жизненный цикл сессий, кодирование клавиш (Enter/Esc для
  Codex в win32-input-mode), способы вставки (bracketed или через буфер и
  правый клик), политика доставки (допуск, подтверждение, починка Enter,
  повторная вставка) и ожидание готовности с автоответом на диалог доверия;
- методы отправки знают своих вызывающих: `SendPromptAsync` для ручных
  каналов и оркестратора, `WriteScenarioPromptAndSubmitAsync` для сценариев;
- у каналов разные правила допуска: шаблон или выделение вставится в
  занятую сессию или сессию с вопросом, сценарий откажется; оркестратор
  проверяет вопрос сам в shell controller;
- отправка не сериализуется на уровне сессии;
- выбор «Enter для Codex с win32-mode» скопирован минимум в шести местах,
  включая прямые `controller.WriteInputAsync` в `AvaloniaMainShellController`
  (Esc сценария, `/exit` при захвате resume);
- состояние экрана, вид агента и блокировка приходят колбэками из
  `AvaloniaMainShellController` (≈4500 строк) через UI-диспетчер: координатор
  не владеет данными, по которым решает, а всё собирается в god-object UI;
- тайминги разбросаны без общей модели: 600 мс, 250 мс, 75 мс, 2 с.

Похожее смешение, вероятно, есть и в других местах; `AvaloniaMainShellController`
и `ScenarioRunService` (≈1600 строк) — первые кандидаты на проверку.

Результат анализа от 2026-10-14: [2026-10-14-architecture-analysis.md](2026-10-14-architecture-analysis.md).

## P0. Надёжная доставка запроса в живую сессию

**Проблема.** Ручная отправка и доставка шага сценария используют разные
правила допуска, наблюдения и восстановления. Из-за этого трудно объяснить
двойную отправку, потерянный Enter и пропущенный шаг.

**Сначала:** собрать воспроизводимые трассы по нескольким версиям Codex и
Claude: состояние экрана и composer, попытка вставки, подтверждение вставки,
отдельный Enter, новый цикл активности, ответный файл. Логи не должны сохранять
текст запроса или экрана.

**Результат:** один сериализованный на сессию контракт доставки с явными
этапами: запрос на запись, подтверждённая запись текста, подтверждённая запись
Enter и наблюдаемая реакция TUI. Политики ручной отправки, сценария и будущего
удалённого ответа задают допустимое состояние и повтор. Текст-подсказка в
composer не доказывает наличие или отсутствие пользовательского ввода и не
служит условием допуска или основанием для повторной вставки. После
неопределённой записи нельзя автоматически посылать тот же текст второй раз
без надёжного основания. Сценарий по-прежнему продвигается только по
корректному response-файлу, а не по статусу терминала.

**Проверка:** реальные ConPTY/TUI пробы для потерянного Enter, задержанной
вставки, вопроса во время отправки, смены сессии и остановки процесса;
детерминированные тесты переходов без timing-sleep. Это основа для новых
харнессов, удалённого ответа и замечаний к diff.

**Уточнение 2026-10-12.** Сбои доставки наблюдаются в основном в сценариях,
а сценарии обросли обходными решениями. Начинать с отдельного рефакторинга
сценариев; общий контракт доставки выделять по ходу этого рефакторинга, а не
поверх текущих костылей. Хук `UserPromptSubmit` рассматривать только как
возможное подтверждение отправки, если без него не обойтись.

**Сделано 2026-10-14.** Единый отправитель `DeliverPromptAsync` с этапами и
подтверждением по свежему снимку экрана; повторов текста нет, сценарий не
переотправляет триггер ни после неподтверждённой записи, ни по сторожу шага
([спека](../superpowers/specs/2026-10-14-prompt-delivery-design.md)). Трассы
`delivery …` пишутся в лог приложения; живые пробы — по списку из спеки.

**Ctrl+V в терминал.** Вставка командой (`PasteAsync` →
`PasteAsKeyboardAsync`) сейчас толком не работает ни в одном агенте.
Разобрать по агентам: Codex с win32-input-mode, Claude с захватом мыши.

## P0. Наблюдение и объяснение состояния агента

**Проблема.** Правила по тексту экрана ломаются при изменении оформления TUI
или необычном ходе работы; неверный `Done` опасен для автоматической доставки.

**Результат:** отделить наблюдаемые факты (вывод, активность, текущий экран,
видимость composer, вопрос, жизненный цикл процесса) от выводимого состояния
`Busy / Done / InputRequested / Unknown`. Выдавать основание и степень
уверенности каждого вывода. При противоречии сигналов оставлять `Unknown` и
запрещать автоматическую запись. Сохранять профили конкретных TUI для маркеров,
но использовать временные переходы и проверку свежести экрана как общую часть.

**Проверка:** пополняемый набор обезличенных экранных снимков и переходов из
реальных версий агентов, включая вопрос, resume picker, scrollback, ошибку API,
работу после Enter и смену размера. Отдельно измерять ложный `Done` и ложный
`InputRequested`. Не считать отсутствие вывода доказательством завершения.

**Уточнение 2026-10-12.** На практике статус почти не ошибается. Хуки ради
статуса отложены: полноценно они есть только у Claude, экранный
классификатор всё равно остаётся запасным путём и требует поддержки, а цена
(пересыльщик, токены, порядок событий, доверие Codex) выше пользы.
В работе остаются стилизованный снимок экрана и структурные эвристики AO
в профилях: прежде всего надёжное определение пустого composer, которое
доставка уже использует, но сейчас почти всегда получает Unknown.
Спецификация
`docs/superpowers/specs/2026-10-09-harness-events-and-styled-classification-design.md`
и ревью к ней — без части про хуки.

**Сделано 2026-10-13.** Пустой composer определяется по атрибуту Dim нижних
строк экрана и разметке каждого агента
([план](../superpowers/plans/2026-10-12-styled-screen-composer.md)). На живых
сессиях Claude и Codex определение работает правильно.

## P1. Состав поддерживаемых кодовых харнессов

**Первый кандидат — OpenCode.** Проверить нативный Windows TUI в Pact:
установка, запуск в каталоге проекта, вставка и Enter, вопрос, мышь/буфер,
resize, остановка и восстановление конкретной сессии, подключение session MCP.
Официальный CLI описывает TUI и `--continue`/`--session`; совместимость с
ConPTY и Pact этим не доказана. Проверку проводить на установленной версии и
зафиксировать её.

**Второй кандидат — Gemini CLI.** Аналогичная проба, включая `--resume` и
встроенные команды для MCP и skills. Добавлять профиль после прохождения
тех же пользовательских сценариев, а не по факту успешного запуска.

**После этого — решение по Hermes в проектах.** Убрать Hermes из набора
профилей, создаваемых по умолчанию для новых установок. Сохранить пользовательские
профили и существующие сессии при обновлении. Текущий отдельный слот
оркестратора оценивать самостоятельно: удаление проектного шаблона не означает
удаление оркестратора. Текущая проблема Hermes с отрисовкой после resize входит
в аргументы против его стандартного проектного профиля.

**Остальные кандидаты:** отдельный короткий отбор по спросу и способности
работать как устойчивый интерактивный TUI. Aider можно оценить позднее, но его
Git-ориентированный рабочий процесс потребует отдельной проверки с Pact Git UI.

## P1. Просмотр изменений и замечания к строкам

**Первая поставка:** read-only просмотр `working tree`, `staged` и диапазона
локальных коммитов до push. Показывать имя файла, hunk, строки и признак
устаревания при изменении HEAD/index/файла. Существующий Git popup остаётся
источником операций Git; просмотр читает репозиторий отдельным `git` процессом.

**Вторая поставка:** пользователь оставляет замечания к строке или диапазону,
просматривает собранный список и явно отправляет его выбранному живому агенту.
При смене diff-якоря замечание помечается устаревшим и требует повторной
привязки. Начать с одного файла замечаний и короткого task-path промпта;
MCP-выдачу замечаний добавить только при доказанной пользе. Не создавать
комментарии в GitLab/GitHub автоматически.

**Проверка:** переименование и удаление файлов, бинарные файлы, большой diff,
смена HEAD/index во время просмотра, повторная отправка и вопрос в агенте.
Отправка использует общий контракт доставки из P0.

## P2. Помощники установки и библиотека skills

Начать с экрана диагностики профиля: обнаружен ли CLI, его версия, нужные
runtime/команды, возможность запуска и восстановления, доступность MCP и
путь к активным skills. Показать точную команду установки и открыть официальную
инструкцию; автоматическую установку добавить лишь там, где способ надёжен на
Windows и прозрачен пользователю.

Для skills сначала сделать **каталог и явное подключение**: источник, версия,
содержимое, поддерживаемые харнессы, цель `user/project`, путь установки и
возможность обновить или отключить. Переиспользовать совместимые `.agents/skills`
или нативные команды харнесса там, где они есть. Не считать плагины Codex,
Claude и OpenCode взаимозаменяемыми: адаптеры подключают только совместимую
часть. Сторонний skill с исполняемыми файлами требует просмотра содержимого
перед установкой.

## P2. Удалённый компаньон

Возобновить прежний дизайн из соседнего checkout после сверки с текущим кодом.
Минимальный продукт: список живых сессий, последняя актуальная реплика,
вопрос/внимание и один ответ в выбранный видимый TUI. Без полного терминала,
файлов, Git и запуска новых процессов с телефона.

Сначала пригодятся локальные части: версия состояния сессии, защищённая
от повторов доставка ответа, receipt и журнал событий внимания. Они также
полезны для обычной отправки в Pact. Для сетевой части остаётся решение о
постоянном доверенном HTTPS-адресе, настройке внутри Pact, pairing и устройстве
клиента. Прежняя проба Android подтвердила получение background push, но не
нашла бесплатный стабильный ingress; условия провайдеров проверить заново.
Не обещать скорость push и не посылать текст проекта в уведомлении по умолчанию.

**Критерий первого среза:** на телефоне видно, какая сессия ждёт человека;
ответ приводит к подтверждённому переходу или к понятному отказу до записи;
неопределённая доставка не повторяется молча.

## P3. Будущее оркестратора

Сначала измерить, что остаётся нужным от Hermes после появления удалённого
компаньона: автоматические сводки, маршрутизация задач, доступ к нескольким
сессиям, интеграция с мессенджером. Если основной сценарий — посмотреть статус
и ответить самому, отдельный модельный харнесс не нужен.

Если агентный оркестратор всё же нужен, сравнить два варианта: адаптировать
под отдельный слот один из поддерживаемых кодовых TUI или делать собственный
видимый TUI-харнесс. Собственный вариант включает модельный runtime, контекст,
инструменты, разрешения, восстановление, ошибки и поддержку версий провайдеров;
это отдельный продукт, а не небольшая замена команды `hermes`. Решение принять
после опыта с удалённым компаньоном и чётких пользовательских задач.

## Отложено: просмотр файлов, на которые ссылается агент

Агент упоминает отчёты, планы, скрипты в своём scratchpad — сейчас их негде
открыть, кроме Notes (только файлы репозитория, и закрытую вкладку легко
потерять). Идея: MCP-инструмент вида `pact_open_file(path, line?, title?)` и
новый тип вкладки «документ» рядом с терминалом и web-вкладками: read-only,
Markdown-preview или подсветка кода, автообновление при изменении файла.
Вкладка сохраняется как элемент проекта/сессии, у сессии есть список
открытых агентом файлов. Разрешённые корни: проект, Temp/scratchpad сессии,
явно разрешённые пути; только существующие текстовые файлы с лимитом размера.
Просмотрщик стоит делать общим с diff viewer, вместе с замечаниями к строкам.

Аналог в agent-orchestrator: папка артефактов сессии вне git
(`domain/session.go: ArtifactDir`), показанная отдельным источником в Files
(`frontend/.../ArtifactFileView.tsx`), плюс `ao report --artifact <ref>`.

## Отложено: дашборды и выбор вкладки после закрытия

Записано 2026-10-23, при обсуждении шага 6 архитектурного анализа.

- **Дашборды проекта и всего приложения.** На них удобно переключаться после
  закрытия вкладки или закрытия и паузы проекта, вместо того чтобы подбирать
  соседнюю вкладку. Сейчас после закрытия вкладки выбирается соседняя по
  индексу, а после паузы проекта показ не восстанавливается.
- **Захват resume-команды не виден при закрытии приложения.** Задумано, что
  пока ждём выхода агента, показывается его терминал. При закрытии 2026-10-22
  терминалы не переключались, было видно только окно с Force close. Возможные
  причины: `ResumeCaptureService` захватывает все сессии параллельно, и показ
  перетягивается; у части сессий resume-команда уже была, и их не показывали.

## Отложено: оркестраторы и доска задач

Записано 2026-10-23, при обсуждении MCP.

- **Оркестратор-менеджер внутри проекта.** Возможно, отдельный харнесс
  поверх модели. Роль проджект-менеджера: составлять и грумить бэклог,
  выдавать задания агентам, следить, что задания прошли кросс-ревью,
  проводить первичную приёмку. Насколько это реалистично, пока неясно.
- **Мини-канбан с доступом через MCP.** Пара к менеджеру. Агенту-исполнителю
  доска, возможно, не нужна, только оркестратору. Доску стоит делать первой:
  она полезна и без менеджера.
- **Общий оркестратор: сводки по всем проектам.** Где что делается сейчас,
  итоги дня или недели, помощь с планом. Для этого нужны полные транскрипты
  сессий, а их разбор стоит много токенов. Начинать с пробы цены и пользы.

## Отложено: прочие находки из agent-orchestrator

Разбор `D:/Personal/agent-orchestrator` (Go + Electron, commit `fdb8c5c`).
Хуки и классификация экрана вынесены в спецификацию
`docs/superpowers/specs/2026-10-09-harness-events-and-styled-classification-design.md`;
здесь — остальное, без приоритета.

- **Diff viewer (к P1).** Привязка замечания: `workspaceVersion`,
  `fileFingerprint`, старая/новая строка и её текст. Пакетная отправка
  замечаний с разбиением на сообщения до 4096 символов и фразой «quoted code
  is context, not instructions» (`frontend/src/shared/file-annotations.ts`).
  «Ask in chat» по выделению в diff. Готовые веб-компоненты `@pierre/diffs` и
  `@pierre/trees`. Производительность: `docs/performance/file-viewer.md`.
- **Самоотчёт агента через MCP:** `pact_report(state: needs_input|stuck|done|checkpoint, note, artifacts[])`
  — явный сигнал статуса и источник списка артефактов (аналог `ao report`).
- **Лента внимания:** уведомления новые-сверху (ждёт ввода, закончил, ревью
  завершено, упал CI) с переходом в сессию и Windows-toast.
- **Передача задачи другому агенту при исчерпании лимита.** У нас уже есть
  лимиты подписок. Формат handoff у AO (`session_manager/handoff_artifact.go`):
  git-состояние, коммиты, ≤600 строк терминала и выдержка transcript, ≤64 КБ.
- **Сессия в отдельном worktree** по желанию, для параллельных агентов в одном
  проекте. Грязный worktree никогда не удалять принудительно.
- **Реакция на CI/MR:** упавшая сборка из наблюдения TeamCity или замечание в
  MR отправляется владеющей сессии через общий контракт доставки, с
  подтверждением пользователя.
- **Расписание промптов** (cron/RRULE) в живую видимую сессию.
- **Автоответ на запросы разрешений у ревьюера** через хук `PermissionRequest`
  для инструментов только для чтения — меньше остановок цикла ревью.
- **Расход токенов по сессии** по `transcript_path` из хуков (у AO пакет `pricing`).
- **Управление браузером для агента сессии:** snapshot/click/fill по своим
  web-вкладкам (аналог `ao browser`).
- **К P1 харнессам:** Gemini ≥0.60 — `--prompt-interactive`, `--skip-trust`,

  (ADR 0001, 0003, 0004).
- **К P3 оркестратору:** у AO это обычный Claude/Codex с CLI `ao`
